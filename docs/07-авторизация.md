# Регистрация и авторизация задания 7

Учётная запись создаёт серверный сеанс и открывает защищённый профиль. Редактор остаётся доступен гостям: фотографии обрабатываются в браузере, проекты в облаке пока не сохраняются.

## Хранение и проверка

server/auth.mjs использует асинхронный scrypt стандартной библиотеки Node.js: N=131072, r=8, p=1, результат 64 байта, случайная соль 16 байт на каждую запись. Параметры соответствуют выбранному варианту рекомендации OWASP. Пароль имеет длину 15–128 символов, не обрезается и не записывается в журнал. Сравнение результата выполняется timingSafeEqual. Для неизвестного email также выполняется дорогой расчёт; сообщение неверного входа одинаково.

Email нормализуется в нижний регистр и служит логином. Подтверждение владения адресом не реализовано: нельзя использовать его как доказательство личности. Повторная регистрация отклоняется, в том числе при двух одновременных запросах. Отдельные случайные соли дают разные хеши одинаковых паролей.

Файл data/users.json находится за пределами dist, исключён из Git. Новый список записывается во временный файл и атомарно заменяет прежний; изменения сериализуются в одном процессе. Ограничение — до 10000 записей. В Linux файлу задаётся режим 0600, каталогу 0700. Windows mode не заменяет ACL: папка должна быть закрыта для посторонних учётных записей средствами Windows. Ограничить нужно и резервные копии. JSON не зашифрован; email доступен администратору диска. Для нескольких процессов или большого числа пользователей требуется СУБД с транзакциями и уникальным индексом.

## Сеансы и запросы

Случайный токен 32 байта передаётся через cookie wps_session с HttpOnly, SameSite=Strict и Path=/. JavaScript не получает токен через API и не хранит его в localStorage. На сервере хранится SHA-256 токена и срок действия 8 часов. При входе текущий токен отзывается и создаётся новый; при выходе запись удаляется и cookie очищается. После перезапуска сервера все сеансы прекращаются, учётные записи остаются.

Изменяющие запросы требуют совпадения Origin с APP_ORIGIN либо текущим HTTP-адресом. CORS для сторонних сайтов не включён. До 20 попыток регистрации/входа за 15 минут с одного socket IP; заголовку X-Forwarded-For сервер не доверяет. За прокси все пользователи могут делить один лимит: доверие конкретному прокси и распределённый лимитер относятся к следующему этапу. Одновременно вычисляются не более двух хешей, иначе ответ 503. Это ограничивает память процесса; scrypt требует порядка 128 МиБ на расчёт.

Тело ограничено 8192 байтами, поддерживается JSON. API возвращает no-store, сервер — nosniff, Referrer-Policy, X-Frame-Options и CSP. Серверная проверка профиля выполняется при каждом GET /api/auth/me; сокрытие кнопок не является контролем доступа.

## API

| Метод и путь | Результат |
| --- | --- |
| POST /api/auth/register | email и password в JSON; 201, профиль и cookie |
| POST /api/auth/login | email и password; 200 либо общий ответ 401 |
| GET /api/auth/me | 200 с id и email только при действующем сеансе; иначе 401 |
| POST /api/auth/logout | Отзыв текущего сеанса и очистка cookie |

В ответах отсутствуют соль и хеш. Возможны 400, 403, 409, 413, 415, 429 и 503 по соответствующим ограничениям. Ошибка 409 при регистрации позволяет определить существование email; это известный компромисс учебной реализации. Для публичного сервиса нужен нейтральный сценарий регистрации с подтверждением почты.

## Запуск

Для локального показа: npm run build, затем npm start и http://localhost:3001. Настройки сетевого доступа, существовавшие до задания, сохранены. Для входа с настоящим паролем через локальную сеть сначала нужен HTTPS. Для изолированного показа на одном ПК можно задать переменную HOST=127.0.0.1.

Для HTTPS за обратным прокси задайте APP_ORIGIN=https://editor.example. Origin должен точно совпадать с внешним адресом; cookie получает Secure. Прокси завершает TLS и передаёт запросы этому серверу. DATA_DIR задаёт закрытый каталог учётных записей. Переменные .env автоматически не подгружаются; пример — в .env.example.

Нет восстановления пароля, MFA, подтверждения email и управления всеми сеансами пользователя. TLS на самом Node.js сервере не настраивался, публичный хостинг не развёрнут. Это рабочая учебная реализация базовой авторизации, а не завершённая система управления идентификацией.

## Проверка

Автотесты используют отдельные временные каталоги и проверяют регистрацию, дубли и гонку, вход, неверные данные, поддельную cookie, отзыв/ротацию/истечение сеанса, перезапуск, Origin, HTTPS cookie, соль, лимит запросов, JSON и размер тела. В браузере проверены регистрация, перезагрузка, выход, повторный вход, эффект выбранного слоя и отмена. Снимки находятся в verification/task67. Тестовый email на .test — искусственный; реальные данные пользователя в тестах не использовались.
